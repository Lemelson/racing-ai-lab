# Предлагаемая архитектура

> Обновление 26 августа 2026: рабочий vertical slice уже реализован как локальное browser-приложение на нативных ES modules и Canvas без внешних runtime-зависимостей. Это позволило проверить редактор, обучение и UI до дорогого переноса ядра. Ниже описана целевая архитектура для следующего этапа; MVP зафиксирован в [06-mvp-implementation.md](06-mvp-implementation.md).

## Вывод

Оптимальная первая полноценная версия — не Pygame-скрипт и не большой игровой движок с обучением внутри кадра. Это два независимых слоя:

1. Детерминированное headless-ядро быстро считает физику, сенсоры, fitness и поколения.
2. Визуализатор показывает редкие snapshots или сохранённый replay с удобной скоростью.

Так можно одновременно видеть обучение и не ограничивать его частотой монитора.

## Рекомендуемый стек

| Часть | Выбор | Почему |
|---|---|---|
| Ядро симуляции | Rust, нативная ARM64-сборка | Высокая скорость без Python overhead, строгие контракты и безопасный параллелизм. |
| Параллельная оценка | Rayon, сначала CPU | Независимые машины и эпизоды естественно распределяются по ядрам; [Rayon](https://docs.rs/rayon/) предоставляет data-parallel iterators и гарантии отсутствия data race. |
| Визуализатор | Bevy 2D поверх wgpu | Есть окно, sprites, камера, UI и путь к будущему 3D. [wgpu](https://wgpu.rs/) нативно работает через Metal на macOS. |
| Формат данных | Версионированные config + metrics + replay | Результат можно повторить, сравнить и показать без повторного обучения. Конкретный формат выберем при реализации. |
| Графики | Встроенная панель viewer + экспорт табличных метрик | Живой просмотр и отдельный точный анализ не зависят друг от друга. |
| Участники | Отдельный Rust crate на модель за стабильным trait | Одинаковый язык, скорость и доступ к среде; модель не может случайно изменить физику соперника. |

## Почему не Pygame как основной стек

Pygame прекрасно подходит для учебного прототипа и помог автору быстро показать идею. Но Python-цикл, пошаговые лучи и отрисовка каждой машины станут основными ограничителями при масштабировании.

Кроме того, современный ускоренный SDL2 API в документации Pygame всё ещё помечен как экспериментальный и меняющийся: [pygame._sdl2](https://www.pygame.org/docs/ref/sdl2_video.html). Pygame можно использовать для очень раннего throwaway-прототипа, но нет смысла сначала строить архитектуру, которую затем придётся переносить.

## Почему не Macroquad

Macroquad выглядит почти идеальным лёгким 2D-вариантом и заявляет efficient batching и поддержку macOS. Однако в RustSec остаётся информационное предупреждение о soundness без исправленной версии: [RUSTSEC-2025-0035](https://rustsec.org/advisories/RUSTSEC-2025-0035.html). Для нового долгоживущего проекта безопаснее выбрать другой viewer.

## Почему не Unity/C# или Godot

Они способны хорошо нарисовать эту задачу, но в первой 2D-версии редактор, scene model и большой runtime дают больше инфраструктуры, чем пользы. Главная нагрузка здесь — миллионы детерминированных шагов маленькой симуляции, а не сложная графика.

Если главной целью станет красивая 3D-игра, а не исследовательская лаборатория, решение надо пересмотреть. Тогда Godot или Unity могут стать отдельным viewer, сохраняя прежнее headless-ядро.

## Почему GPU не включается автоматически

M1 Max имеет сильный Metal GPU, но задача из ролика использует очень маленькие сети. Для единичных маленьких матриц стоимость подготовки и синхронизации GPU может быть больше самой математики. Физика, collision и sensors также остаются ветвящимся кодом, удобным для CPU.

Правильный подход:

1. Сначала сделать пакетированную структуру данных и быстрый CPU baseline.
2. Измерить steps/sec на реальном M1 Max.
3. Отдельно проверить MLX и при необходимости PyTorch MPS на больших batch.
4. Оставить backend, который быстрее на полном поколении, а не только на умножении матриц.

[MLX](https://developer.apple.com/videos/play/wwdc2025/315/) специально создан для Apple Silicon, поддерживает CPU/GPU, unified memory, vectorization и compilation. [PyTorch MPS](https://developer.apple.com/metal/pytorch/) также использует Metal. Оба варианта реальны, но их преимущество здесь должно быть доказано benchmark.

## Логическая схема

```text
Track + Physics + Sensors + Scoring  (замороженная общая среда)
                    |
                    v
             Competitor API
          /                   \
 ChatGPT trainer/policy   Gemini trainer/policy
          \                   /
                    v
      snapshots + metrics + checkpoints + replay
                    |
                    v
          Bevy viewer / final race / reports
```

## Быстрое ядро

### Физика

- фиксированный timestep;
- простая 2D bicycle/kinematic model;
- throttle, brake и continuous steering;
- одинаковые ограничения скорости и руления;
- без сложного физического движка на первом этапе.

### Трасса

Картинка может оставаться визуальным слоем, но истинная геометрия не должна зависеть от цвета отдельного пикселя. Предпочтительны:

- центральная линия с длиной и контрольными точками для прогресса;
- границы трассы как геометрия либо предвычисленная signed distance field;
- spatial index или distance grid для быстрых сенсоров;
- несколько учебных, validation и закрытых test-трасс.

### Данные популяции

- хранить одинаковые поля машин плотными массивами;
- не создавать тысячи тяжёлых игровых объектов;
- вычислять действия и физику batch-операциями;
- параллелить по эпизодам или независимым группам машин;
- исключить выделения памяти из горячего цикла.

### Визуализация

Viewer не управляет временем обучения. Он получает snapshot, например, несколько раз в секунду и может показывать:

- всех живых машин либо выборку;
- лидера и лучшего представителя предыдущего поколения;
- сенсоры выбранной машины;
- best, median и percentile fitness;
- generation, elapsed time и simulation steps/sec;
- переключение ChatGPT/Gemini;
- паузу, один шаг, real-time, ускорение и max-speed;
- просмотр сохранённого replay после завершения.

## Режимы работы будущей программы

| Режим | Назначение |
|---|---|
| Manual | Проверка физики человеком с клавиатуры. |
| Debug | Одна или несколько машин, сенсоры и подробные overlays. |
| Train | Headless, максимальные steps/sec, только метрики и редкие snapshots. |
| Watch live | Обучение быстро идёт в фоне, viewer показывает sampled state. |
| Replay | Плавный просмотр сохранённого эпизода без пересчёта обучения. |
| Benchmark | Повторяет набор seeds и выдаёт сравнимый отчёт. |
| Final race | По одному замороженному лучшему checkpoint на закрытой трассе. |

## Порядок реализации

1. Benchmark-пустышка: измерить максимально простой tick loop на M1 Max.
2. Детерминированная физика и ручное управление.
3. Геометрия трассы, прогресс, collision и тесты.
4. Сенсоры и batch evaluation.
5. Headless runner и replay.
6. Viewer и графики.
7. Стабильный API участника.
8. Простой общий baseline, чтобы проверять среду.
9. Выдача задания ChatGPT и Gemini.
10. Повторные прогоны и финальный benchmark.
